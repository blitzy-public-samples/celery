# Global Rate Limiter — Decision Log & Traceability

This log records the non-trivial design decisions behind the opt-in, Redis-backed **global (cross-worker) rate limiter** for Celery workers, and provides a 100%-coverage requirement → file → test traceability matrix. Per the minimal-change discipline, design rationale lives **here** rather than in code comments, so the touched source stays comment-light — the single permitted in-code comment is `# required for global (cross-worker) rate limiting` in `celery/worker/consumer/consumer.py`. The feature is **opt-in and default-off**: it activates only when `worker_enable_global_rate_limits=True` and a task already carries a `rate_limit`; when disabled, the dispatch path is byte-for-byte identical to today's per-worker limiting. Feature context: Celery 5.6.x; settings `worker_enable_global_rate_limits` (bool, default `False`) and `global_rate_limit_url` (str, default `None`).

## (A) Decision Log

| Decision | Alternatives considered | Rationale | Risk |
| --- | --- | --- | --- |
| Hook `bucket_for_task()` rather than `strategy.get_bucket`. | Branch inside the strategy gating closure; add a parallel decision path. | `bucket_for_task()` (`celery/worker/consumer/consumer.py` L296-298) is the single bucket-construction site; substituting the bucket object there leaves `celery/worker/strategy.py` (L190-203, `if bucket: return limit_task(req, bucket, 1)`) and the entire deferral loop byte-for-byte unchanged, because they operate on whatever object `task_buckets` holds. | `reset_rate_limits()` (also invoked by the remote-control handler `celery/worker/control.py` L284 and on worker restart `celery/worker/worker.py` L275) re-calls the hook, so it must rebuild idempotently; mitigated by a single reused, lazily-created limiter client (`_global_rate_limiter` `cached_property`). |
| Register the `global` settings namespace via dictionary expansion (`**{'global': Namespace(rate_limit_url=Option(None, type='string'))}`). | `global=Namespace(...)` (raises `SyntaxError` — `global` is a reserved word); placing the URL under the `worker` namespace (would produce the wrong flat key). | Yields the EXACT required flat key `global_rate_limit_url` while sidestepping the reserved word; `flatten()` prefixes the namespace name to the option name. | Minimal; the uppercase compat alias `GLOBAL_RATE_LIMIT_URL` (and `CELERYD_ENABLE_GLOBAL_RATE_LIMITS` for the worker flag) is standard Celery behavior and harmless (lives in the OLD/compat tables, not in `SETTING_KEYS`). |
| Atomic Lua script using Redis `TIME` instead of `WATCH`/`MULTI`. | `WATCH`/`MULTI` optimistic transaction; client-side lock (`SETNX`/Redlock); `INCR` fixed-window counter. | One server-side round trip with no read-modify-write race across workers; the Redis server clock (`TIME`) avoids worker clock skew; `WATCH`/`MULTI` requires client retries under contention. | Lua correctness and bounded key growth; mitigated by `EVALSHA` caching (via redis-py `register_script`) plus a key TTL. |
| Cache `retry_after` to satisfy the `expected_time()` contract. | A second Redis round trip inside `expected_time`; compute the delay locally. | The deferral loop calls `can_consume()` then `expected_time()` back-to-back (`celery/worker/consumer/consumer.py` L341-349); the Lua script returns `[allowed, retry_after]`, so caching the returned `retry_after` gives a consistent value from the SAME atomic decision with zero extra round trip. | If `expected_time()` is somehow called first (no cached value yet), a safe default delegates to the internal local `TokenBucket`. |
| `capacity = 1` (no burst). | `capacity = rate` (allow a full one-second burst); a configurable capacity. | Mirrors the existing `TokenBucket(limit, capacity=1)` (`celery/worker/consumer/consumer.py` L298) EXACTLY, so enabled/disabled semantics stay consistent and no new burst behavior is introduced. | None beyond intent (matches current per-worker semantics). |
| Fail-open over fail-closed. | Fail-closed (deny while Redis is down); drop / reject / dead-letter the task. | The prompt forbids blocking task processing; on ANY Redis error the limiter logs a WARNING and delegates to an internal local `TokenBucket(rate(limit), capacity=1)`, degrading gracefully to today's per-worker behavior. | During a Redis outage the global guarantee relaxes to per-worker (aggregate may reach `N×R`) — documented and acceptable; fail-closed would risk task starvation. |
| Bounded key TTL (`EXPIRE` inside the Lua script). | No TTL (keys live forever); a manual cleanup job. | Bounds Redis key growth for tasks/rates that fall idle; self-healing. | A key expiring between calls resets the bucket to full — harmless (at most one extra token allowed after an idle period). |
| URL fallback `global_rate_limit_url` → `result_backend` → `broker_url`. | Always require `global_rate_limit_url`; always use the broker URL. | Zero-config when the deployment already uses Redis as broker/result backend; reuses existing connection info; an explicit override remains available via `global_rate_limit_url`. | A non-Redis resolved URL (e.g., `memory://`, `cache+memory://`) puts the limiter in permanent fail-open mode; documented — operators set `global_rate_limit_url` to a Redis endpoint to guarantee global enforcement. |
